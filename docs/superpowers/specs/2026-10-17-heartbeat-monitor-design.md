# 模组自检与 ECS 心跳监控设计

日期：2026-10-17。状态：用户确认方案，并要求先完成 iStoreOS，ECS 单独新建仓库。

## 本次分期与仓库边界（用户最新要求）

本仓库本阶段只实现 iStoreOS 端：自检、配置/状态网页、鉴权心跳发送及协议文档，
用本地 HTTPS 测试接收器验证上报，不把 ECS 实现加入本仓库。
ECS 接收、状态机、Bark 报警、Alpine/OpenRC 部署将在独立新仓库构建；
下文 ECS 章节仅规定跨仓库协议及后续目标，不作为当前阶段上线前置条件。
本地测试接收器只属于测试夹具，不作为 ECS 产品代码发布。
独立仓库的名称、所在组织及远程创建将在 ECS 阶段确认，当前不代猜 GitHub 仓库位置。

## 1. 需求与范围

在现有 iStoreOS 短信专用服务中增加自检与心跳；用户 ECS 运行 Alpine Linux，
独立部署接收/监控程序，不以 Docker 为运行前提。每 10 分钟上报一次正常心跳，
连续两个周期未收到正常心跳（默认 20 分钟）由 ECS 通过 Bark 报警。

保持现有收发短信、归档、Bark/TG 转发及 TG 二次确认功能，保持模组移动数据关闭。
不通过实际发送短信自检，不新增拨号、自动重启模组或网络恢复行为。
ECS 自身失效需要外部监控，不由本设计承诺覆盖。

## 2. 双端架构

- iStoreOS：进程内自检工作器、心跳工作器、私有配置及本地网页设置。
- ECS：在独立仓库提供 Go 命令 `cmd/vohive-monitor`，接收心跳、持久化监控状态、调度报警。
- ECS 程序仅使用 Go 标准库，可 CGO_ENABLED=0 编译 linux/amd64 和 linux/arm64，
  不链接 libusb/SQLite，不要求安装 Go；目标 CPU 架构部署前通过 uname 核实。
- Alpine 使用专用非 root 用户、OpenRC 服务脚本、私有配置和数据目录。
- ECS 默认监听回环高位端口，通过现有 HTTPS 反向代理公开固定路径；另外支持程序
  直接使用证书文件提供 HTTPS。客户端始终验证证书，不提供跳过验证选项。

## 3. iStoreOS 自检

启动后立即检查，随后默认每 60 秒检查一次。全部条件满足才判定正常：

1. 当前 USB 模组 AT 通信成功，不能只使用旧 connected 缓存。
2. SIM 状态 READY。
3. 蜂窝注册查询显示已注册（本地或漫游）；仅显示运营商名称不足以证明注册。
4. 短信专用数据保护为 off，并有本轮有效的模组数据关闭查询。
5. 短信归档循环最近 150 秒内成功完成过一次存储读取/同步，无当前同步错误。
6. SQLite 当前查询可用；不在每分钟执行昂贵的完整数据库校验。

自检只读，不发送短信、不删除短信、不改变移动数据设置。复用现有模组互斥访问，
避免与收发短信抢读串口。检查耗时超过 45 秒或快照过期超过 150 秒不得报正常；
过期的正常快照不能继续生成正常心跳。归档未完成首次成功同步前为 pending。
低信号作为诊断值，不以任意信号百分比阈值单独判故障。

网页显示总体状态、固定分类检查结果、最近完成时间，不显示短信和敏感硬件身份。

## 4. 心跳调度与配置

- 默认关闭，配置有效并启用后立即自检并发送首个正常心跳；之后默认每 600 秒一次。
- 不健康时不发送正常心跳，ECS 的最后正常时间不会延后。故障分类保留在本地状态。
- 网络发送失败在当前周期内最多重试 3 次，退避 5/15/30 秒；每次发送前重新验证
  本地健康快照仍有效。新周期不补发旧周期心跳，进程重启不恢复历史正常心跳队列。
- 单次 HTTP 超时 10 秒，工作器停止可取消请求。拒绝跨地址重定向，避免认证泄露。
- 可设置：启用、设备 ID（稳定 ASCII 标识）、展示名称、完整 HTTPS 接收地址、
  设备独立共享密钥、心跳周期（默认 600 秒；允许 60—86400 秒）。
- ECS 配置相同周期，默认容忍 2 个周期；有效心跳中的周期必须与 ECS 注册配置相符。
  改周期需先明确同步修改双端，界面与文档提示，不由匿名心跳更改服务器超时规则。
- 配置使用独立 heartbeat.json，目录 0700、文件 0600、原子保存，密钥不进 SQLite、
  URL、日志、浏览器存储和 Git，GET API 不回显密钥；更新设置不要求重新填写未变密钥。
- 配置写入沿用现有回环/Origin 校验。新增配置与状态 API 以及“自检/立即上报”操作；
  手动上报仍须正常自检，不提供无条件报平安按钮。

## 5. 心跳协议与鉴权

固定 POST /v1/heartbeat，JSON 最大 4 KiB；仅正常心跳可刷新服务器计时。
正文包含协议版本、设备 ID、周期、自检完成时间及非敏感检查结果；不含手机号、
ICCID、IMEI、短信正文、Bark key 或 TG Token。

使用每设备独立高熵共享密钥进行 HMAC-SHA256：
- 请求头包含设备 ID、Unix 秒时间戳、随机 128-bit nonce 和签名。
- 签名输入为以换行连接的 `POST`、`/v1/heartbeat`、设备 ID、时间戳、nonce、
  原始请求体 SHA-256 的小写十六进制值；签名为 HMAC 的小写十六进制值。
- ECS 常量时间比较签名、验证正文身份、版本、周期及所有检查为正常，拒绝未知设备。
- 接受时间偏差最多 120 秒；双端需正确校时。计时以 ECS 实际接收时间为准。
- nonce 和首次接收结果随状态持久化，保留至少 5 分钟；重复合法请求幂等返回成功，
  不再次推进最后正常接收时间。同周期重试使用同一正文、时间戳及 nonce。
- 认证失败、无效/异常/过期正文、重复请求都不能延长设备存活时间。
- HTTPS 是部署前提；签名不是允许明文暴露接收接口的理由。

## 6. ECS 设备与状态机

通过私有配置预注册设备（ID、展示名称、共享密钥、周期、超时周期数），不开放匿名注册。
用户当前只需一个设备，数据模型允许多个设备且独立计时。

- 首次启用设备立即开始等待计时，即使从未收到首包也会在 20 分钟后报警。
- 正常心跳更新 last_healthy_received_at。
- 每 5 秒检查，达到 2 × 600 秒未收到有效正常心跳则进入故障事件并排队 Bark 报警；
  正常运行下，默认报警检测在最后正常心跳后 20 分钟至 20 分钟 5 秒之间触发。
- 同一故障事件只发送一条成功报警；发送失败指数退避重试，最长间隔 5 分钟。
- 再次收到正常心跳后进入恢复并发送一次恢复通知；期间不生成重复故障事件。
- 告警未发送即恢复时，以带故障起止时间的合并通知替代尚未发送的告警/恢复二连发。
- Bark 不保证幂等接收：远端已接受但本机尚未持久化即崩溃时可能重发，文档不承诺
  严格 exactly-once；事件 ID 出现在通知中便于识别。

用标准库 JSON 状态文件，0700 数据目录、0600 文件、原子替换及 fsync；
含最后正常接收时间、启用时间、事件、通知重试状态、近期 nonce。
持久化成功后才应答心跳成功。损坏状态启动失败并明确记录固定错误分类，
不悄悄重置时间或给予新的 20 分钟宽限。配置移除设备不再报警，重新新增视为重新启用。
ECS 单实例运行，进程锁防止并发写状态；服务重启恢复原截止时间和未完成通知。

Bark 独立配置到 ECS 私有文件，不依赖 iStoreOS 在线；通知包含设备名、最后正常时间、
超时时长/恢复时间与事件 ID，不包含设备认证密钥。

- iStoreOS：保留现有 UCI/procd 行为，新增配置/状态 UI，重新构建 IPK 并在目标验收。

## 8. 验证门槛

- 自检：AT/SIM/注册/数据/归档/数据库各项失败与陈旧快照均不产生正常心跳。
- 协议：签名、未知设备、篡改、时钟窗口、正文上限、重放、幂等重试、周期不符。
- 调度：启动立即检查、10 分钟周期、健康门禁、失败重试、停用及重配取消旧请求。
- ECS：两个周期边界、首次无首包、故障去重、恢复、Bark 失败、故障未发先恢复、
  进程重启、持久化失败/损坏、重复进程、设备独立性。
- 集成：本地加速时钟测试健康→超时报警→恢复，不以实际等 20 分钟替代边界测试；
  HTTP 接收/自检 UI 的密钥脱敏与跨源写入拒绝。
- 回归：现有 Go race/vet、打包测试；原收发与 TG 控制不受影响。
- 实机：iStoreOS 正常心跳与故障停止，ECS 上线后真实 10 分钟节奏、两周期超时 Bark
  及恢复通知；未部署到实际 ECS 前不宣称真实线上监控已完成。
